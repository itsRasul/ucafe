# Analytics

## Scope and sources

The analytics module reports tenant order outcomes. `orders` is the source of truth for status, customer, event time, and immutable total in integer toman. `clients.id` identifies a unique cafe customer. `coffee_shops.timezone` (default `Asia/Tehran`) defines calendar boundaries. Menu and order-item snapshots, reservations, subscription payments, and payment intents are outside this first endpoint. Subscription gateway payments are not cafe sales.

Orders now snapshot product/category discounts in integer toman, but customer-order settlement, refunds, tax, delivery fees, and profit accounting are not recorded. Order payment is `OFFLINE` only. Consequently `revenueToman` means **delivered payable order value after item discounts**, not confirmed cash collected. A future payment ledger must introduce a separately named paid/refunded metric; it must not silently reinterpret historical delivered value.

## Canonical definitions

| Metric | Rule |
| --- | --- |
| Completed order | Current status `DELIVERED`; counted at `status_changed_at` |
| Cancelled order | Current status `CANCELED`; counted at `status_changed_at` |
| Rejected order | No rejected status exists; there is no rejected count |
| Revenue | Sum of `orders.total_amount_toman` for `DELIVERED` orders at `status_changed_at`; pending and cancelled orders contribute zero |
| Unique customers | Distinct `client_id` among delivered orders in the period; every current order has a cafe-scoped client; no guest orders exist |
| Average order value | Delivered order value / delivered order count, rounded half-up to whole toman; zero when count is zero |

The status constants are in `ordering/order-status.util.ts`, shared with the order domain. Because orders store only the latest status and timestamp, this is a current-state report, not an immutable historical event ledger. A later status correction would restate results. No current API allows changing a terminal order.

## Time and comparison

`analyticsRanges` produces half-open local calendar date ranges `[start, endExclusive)`. PostgreSQL converts each boundary from the cafe's IANA timezone to a `timestamptz` instant. The app process timezone is untouched, and DST changes are resolved by PostgreSQL. An order exactly at a local midnight belongs to the new day.

Supported periods: `today`, `yesterday`, `last7Days`, `last30Days`, `currentMonth`, `previousMonth`, `currentYear`, `previousYear`, and `custom`. Rolling periods include today. Calendar periods use full local days/months/years, including the future portion of an in-progress day/month/year. Custom `start` and `end` are inclusive Gregorian ISO dates, limited to 366 days. Their comparison is the immediately preceding same number of local dates. Calendar month/year comparisons use the previous calendar month/year. `yesterday` compares to the day before yesterday.

`compareMetric` returns `{value, previousValue, change, changePercent}`. All integer fields are decimal strings to retain bigint precision. Percent is a two-decimal string, or `null` when the previous value is zero, including zero-to-zero. Empty sums and counts are `"0"`; AOV is `"0"` with no completed orders.

Time-series contracts are chart-library-neutral: `AnalyticsPoint { bucket, label, value }` and `AnalyticsSeries { key, label, points }`. The granularity model supports hour/day/week/month/year. The Overview endpoint automatically chooses hour for one day, day for 2–45 days, week for 46–120 days, and month for 121–730 days. The custom-range cap currently means year buckets are a supported model but are not selected by this endpoint. PostgreSQL groups delivered orders once for all buckets and produces zero-filled buckets. Hour buckets use UTC instants anchored to local midnight, preserving 23/25-hour DST days; other buckets use local cafe dates. Week buckets are adjacent seven-day spans starting at the selected range's first day, not ISO calendar weeks. Bucket AOV uses the same half-up integer formula.

## Architecture, security, and performance

`GET /api/v1/tenant/analytics/overview` accepts an optional `period` (default `today`) or `period=custom&start=YYYY-MM-DD&end=YYYY-MM-DD`. It returns the period, timezone, local current/previous bounds, chosen granularity, compared revenue, completed orders, cancelled orders, unique customers, and AOV, plus current-period revenue/order/AOV series. Malformed, reversed, oversized, or mismatched range input returns 400. The page exposes all supported periods and a Jalali custom date input; the API receives Gregorian ISO dates and remains authoritative for boundaries and comparisons. The UI displays the previous period through KPI changes and a compact comparison section, without aligning unlike calendar dates in a chart.

The controller requires administrative access token, resolved tenant context, and `analytics.read`. The migration grants this tenant permission to the protected `owner` role; a cafe-specific role may be granted it through existing RBAC. Clients and platform roles have no implicit access. No tenant ID is accepted from the request. The service requires `coffeeShopId`, every SQL query filters `orders.coffee_shop_id`, and responses include no PII.

Analytics is the configurable subscription feature key `analytics`, labeled “آمار و گزارش‌های مالی” in the plan catalog. Golden receives it by default through migration `1787824800000`, which writes only when that key is absent; lower plans remain disabled unless an administrator enables them. This is a seed default, **never a plan-name access rule**. Platform Admin toggles it in the existing plan editor; plan updates preserve unknown feature keys. The effective subscription feature set is authoritative: `SubscriptionsService.requireFeature` enforces it on every Overview request and returns the same `FEATURE_UNAVAILABLE` 403 as other gated modules. Existing trial, active, grace, expiry, upgrade, and scheduled-downgrade logic applies without Analytics-specific lifecycle code. The owner navigation remains permission-aware like Ordering/Reservations; a permitted user whose plan lacks Analytics sees the existing-style unavailable state with a link to plans.

One PostgreSQL query aggregates both periods using conditional `SUM`, `COUNT`, and `COUNT(DISTINCT client_id)`; a second groups current-period outcomes and joins generated buckets. Neither loads order entities or item rows. Existing `(coffee_shop_id, created_at)` and `(coffee_shop_id, status, created_at)` indexes serve order administration, not outcome-time reporting. Phase 0 added `IDX_orders_tenant_status_changed` on `(coffee_shop_id, status, status_changed_at)`; Phase 1 needs no additional index. Check query plans under production volume before adding more indexes or caching. No Redis cache is used.

## Phase 2: time and peak analytics

`GET /api/v1/tenant/analytics/time-distribution` accepts the same period DTO as Overview and returns `period`, `timezone`, `current`, `hours`, `weekdays`, `heatmap`, `dates`, and `peaks`. It uses the same administrative token, tenant context, `analytics.read` permission, and effective subscription `analytics` feature check. No tenant identifier or feature key is accepted from the caller. The frontend adds a **تحلیل زمانی** tab under `/admin/analytics` and shares its period selector with Overview.

The canonical event remains the current `DELIVERED` order's `status_changed_at`; `revenue` is delivered order value in integer toman, represented as decimal strings. PostgreSQL filters by cafe, status, and the half-open local period bounds, then groups by local Gregorian date and local hour with `AT TIME ZONE coffee_shops.timezone`. It returns one row per active date/hour combination, never raw orders. The service sums this bounded result into four complete projections: 24 hour-of-day buckets, seven weekdays in Saturday–Friday order (stable English keys), a 7 × 24 day/hour grid, and every local date in the selected period, including zero dates. An hour bucket combines that hour across all selected dates; it is distinct from Overview's chronological series. The calendar uses the existing 366-day custom-range limit. No new index or migration is needed: the Phase 0 `(coffee_shop_id, status, status_changed_at)` index supports the filter. Query plans should be revisited under production data volume before adding expression indexes or caching.

`peaks` contains arrays `revenueHours`, `orderHours`, `revenueWeekdays`, `orderWeekdays`, `revenueDates`, `orderDates`, and `lowestActiveRevenueDates`. Every bucket tied for the positive maximum is returned in chronological or Saturday-first order. An empty dataset returns empty peak arrays; zero days are never called weakest. The lowest active date considers only dates with completed orders and returns all minimum-revenue ties. Peak labels describe only the selected period, including one-day selections. The UI renders separate bar charts for revenue and orders, a metric-switching weekly heatmap, and daily calendar cells with exact values available by focus, hover, and tap. Persian labels and Jalali date display are presentation only; API dates remain Gregorian ISO. The heatmap and calendar colors are selected by the UI; the API returns business values only.

No payment settlement, refund ledger, historical order events, or recurring-pattern confidence measure exists.

## Phase 3: product and category analytics

`GET /api/v1/tenant/analytics/products` accepts the shared period fields plus `limit` (default 10, maximum 20). It returns a bounded product summary, revenue/quantity/low-performing rankings, absolute-revenue growth and decline rankings, Top 5 plus Others contribution, active products without sales, category rankings, and zero-filled trends for the five highest-revenue categories. `GET /api/v1/tenant/analytics/products/:productId` validates the UUID against the resolved tenant and returns product revenue, quantity, distinct containing-order count, realized average selling price, product revenue share, previous-period comparisons, and zero-filled revenue/quantity trends. Both routes reuse the existing administrative guards, `analytics.read` permission, effective `analytics` feature entitlement, cafe timezone, period ranges, granularity, delivered status, and `status_changed_at` semantics.

Product identity is the stable `order_items.menu_item_id`. Rows whose source item is no longer addressable fall back to a snapshot key derived from `item_name`; these historical rows remain in rankings but do not expose a product-detail link. Active and soft-deleted products display the current product name so renames do not split one product into multiple identities. The response marks unavailable, archived, and no-longer-addressable products. The immutable order-item `item_name` remains the fallback display value.

Product revenue is net realized item revenue after product/category discounts: the sum of immutable `order_items.line_total_toman` for delivered orders. Original unit prices and per-unit discounts remain available from order snapshots for future gross/discount reporting. Quantity is `SUM(order_items.quantity)`, not order-item row count. Orders containing a product/category use distinct order IDs. Average selling price is net item revenue divided by quantity with half-up whole-toman rounding. There are no order-level adjustments or delivery fees, so order totals remain the exact sum of net line totals and product/category revenue reconciles with Overview delivered value.

Migration `1787828400000` adds `category_id_snapshot` and `category_name_snapshot` to order items. New checkout lines copy the owned category at sale time; category aggregation therefore does not reclassify later sales when a product moves or a category is renamed/deleted. The migration backfills existing rows from each product's category at migration time. That is the best recoverable value, but it cannot reconstruct earlier category moves; rows whose product was already unlinked remain `بدون دسته‌بندی`. This pre-migration limitation is explicit and is not presented as exact historical category truth.

Ranking responses never include unlimited rows. Revenue and quantity rankings are separate; the low-performing list includes only products with positive current-period sales, while active available products with zero sales are returned separately. Contribution computes Others from raw revenue (`total - Top N`) before percentage formatting. Percentages are display values truncated to two decimals and never feed financial sums. Growth and decline are sorted by absolute revenue change and also expose the centralized percentage comparison; a zero previous value produces `null`, never infinity. This avoids ranking tiny bases by percentage alone.

The web adds a `محصولات و منو` Analytics tab with summary KPIs, ranking modes, exact-value tables, contribution bars, category performance/trend, tenant-validated product drill-down, growth/decline lists, and a separate zero-sale view. Tables scroll within their panels on narrow screens, selectors remain labeled, charts are keyboard-focusable, and empty/loading/error/entitlement states reuse the existing Persian RTL Analytics surface.

No additional query index was added. Product queries first constrain delivered orders through `IDX_orders_tenant_status_changed` and reach their items through `IDX_order_items_order`; query plans should be checked with production-scale data before adding a product/category expression index. Variant rows remain aggregated under their parent product because the product ID is the stable sale identity. Variant and modifier analytics are deferred; modifiers are not represented as standalone saleable order items.

## Phase 4: customer analytics

`GET /api/v1/tenant/analytics/customers` uses the shared Analytics period query and an optional bounded `limit` (default 10, maximum 20). It has the same administrative guards, tenant context, `analytics.read` permission, and effective `analytics` subscription feature check as the other Analytics endpoints. The response combines period KPIs/comparisons, new-vs-returning count and revenue shares, identified-customer coverage, zero-filled customer trends, repeat-purchase behavior, and bounded revenue/order-count rankings. The UI adds the **تحلیل مشتریان** tab and reuses the global period selector.

Customer identity is `clients.id`, a cafe-scoped stable UUID. Every order requires a `client_id` and the order/client tenant relationship is database-enforced; the current checkout has no guest flow or admin-created customerless orders. Consequently anonymous order/revenue values are zero, while identified-order and identified-revenue coverage are 100% when their denominators exist and `null` when there is no eligible data. No guest identity is inferred. A platform person represented by separate client rows at two cafes is new to each cafe until that cafe has a completed purchase.

Eligible customer activity uses current `DELIVERED` orders at `status_changed_at`, with the same delivered-value revenue definition and half-open tenant-local date ranges as Phase 0. **New** means the customer's first eligible completed purchase at this cafe falls in the selected period; account creation time and orders at other cafes do not affect acquisition. **Returning** means active in the selected period with an eligible completed purchase before its start. Returning customer rate is returning active customers divided by all known active customers; it is not cohort retention. Period revenue is divided by the same known-customer population for average revenue per customer. Average orders per customer is completed known-customer orders divided by unique known customers. Previous-period comparisons reuse the shared calendar comparison boundaries; rate comparisons are calculated by the API.

For each trend bucket, unique customers count once in that bucket and may recur in later buckets. A **new customer** trend counts the bucket containing the first eligible purchase across the customer's complete history. A **returning customer** trend counts active customers whose first eligible purchase predates that bucket's start. Orders later in the same bucket do not change that bucket's status. Daily/hourly/monthly/week buckets use the shared tenant-timezone granularity rules and are zero-filled.

Average days between orders pools the gaps between consecutive eligible completed purchases across the cafe's full history; only actual repeat-purchase gaps contribute, and the result is `null` if no interval exists. Lifetime one-time/repeat counts and the 1, 2–3, 4–5, 6–10, and 11+ distribution cover customers active in the selected period and classify each by lifetime eligible order count to date. Top-10 revenue share uses selected-period revenue from the ten highest-revenue active customers divided by known-customer revenue in that same period. Ranking lists are top-N widgets (not unbounded customer lists); both are selected-period ranked and include current profile display name, period revenue/orders/AOV, lifetime first/last eligible purchase, local days since last purchase, and lifetime totals. Search, full-list pagination, and customer detail are not part of this phase.

Ranking rows use only the stable customer ID for identity and a current name for display; mutable name or phone never splits history. Phone numbers, email, addresses, and authentication data are omitted. Blocked accounts remain in historical purchasing reports. Current client deletion is restricted by order foreign keys. First purchase, last purchase, lifetime metrics, time buckets, and days-since-last-purchase remain tenant-scoped; no platform-global customer history is queried.

The report uses three set-based PostgreSQL queries: one groups the current/previous periods by client and joins cafe-local first purchases, one aggregates active and first-purchase buckets, and one builds lifetime ranking/distribution statistics plus consecutive-order gaps. Migration `1787883600000-CustomerAnalyticsIndex` adds `(coffee_shop_id, status, client_id, status_changed_at)` to support tenant-local lifetime grouping and ordered customer history; the existing `(coffee_shop_id, status, status_changed_at)` index continues to serve period scans. Correct first-purchase classification reads delivered history up to the selected range; if production query plans show that lifetime scans dominate, evaluate a transaction-maintained acquisition timestamp before adding caching or denormalization.

## Phase 5: order and channel analytics

`GET /api/v1/tenant/analytics/orders` accepts the shared period DTO and returns order KPIs/comparisons, current-status distribution, terminal-outcome trend, cancellation value, completed-order item quantity/buckets, fulfillment rows, and source rows. It reuses the Analytics controller's administrative access token, resolved tenant, `analytics.read` permission, effective `analytics` feature check, `analyticsRanges`, timezone, and granularity. It adds no feature key or plan-name check.

The actual order enum is `UNDER_REVIEW`, `PREPARING`, `READY`, `OUT_FOR_DELIVERY`, `DELIVERED`, and `CANCELED`. The four nonterminal values are active; `DELIVERED` is the successful terminal state; `CANCELED` is the unsuccessful terminal state. There is no `REJECTED` state or structured cancellation/rejection reason. No rejected metric is returned. No state-transition history exists, and `status_changed_at` stores the most recent transition time. A completed/canceled order cannot transition again, so its terminal timestamp remains the outcome event time.

**Total orders created** counts every order by cafe-local `created_at` in the selected half-open period, regardless of current status. Status breakdown groups the current status of that created-order population; later transitions can therefore be visible even if they occurred after the selected range. **Completed** and **canceled** counts instead follow Phase 0 and are assigned to the period containing terminal `status_changed_at`. Completion rate is `DELIVERED / (DELIVERED + CANCELED) × 100`; cancellation rate is `CANCELED / (DELIVERED + CANCELED) × 100`. Active orders are excluded from the denominator. If the period has no terminal outcomes, the rates are unavailable (`null`). The same formulas are applied to the previous range. There is no rejection rate because the domain has no rejected state.

Cancelled Order Value is the sum of immutable `orders.total_amount_toman` for currently canceled orders whose `status_changed_at` falls in the period. It describes the submitted order amount, not collected revenue or financial loss; customer orders currently use offline payment and the system does not record settlement. Average items per order is `SUM(order_items.quantity) / completed orders`, where completed orders use the canonical terminal timestamp. It is rounded half-up to two decimal places and compared with the previous period. Completed-order size buckets are `0`, `1`, `2`, `3–4`, `5–7`, and `8+` items; zero is retained defensively although checkout requires at least one line.

Fulfillment uses the existing `PICKUP` and `COURIER` enum. Each row reports created orders by `created_at`, completed orders and delivered order value by `status_changed_at`, AOV (`delivered value / completed orders`, half-up whole toman), created-order share, completed-order share, and revenue share. Source and fulfillment are separate dimensions. Current source is the typed `order_source` enum value `PUBLIC_CLIENT`, assigned by the authenticated public-client checkout path. Migration `1790331236284-AddOrderSource` adds the enum and a nullable column without backfilling history; null historical values are returned as `UNKNOWN`. No tenant-admin cafe order-creation flow exists. `PUBLIC_CLIENT` does not distinguish website from QR access, and it is not marketing attribution. Visits, scans, sessions, and campaign tags are not stored, so conversion/ROI are unavailable.

Source rows report created orders/order share by `created_at`, completed orders, delivered value/revenue share, and AOV by terminal `status_changed_at`, with current and previous comparisons. Source rows sort by delivered value, then created order count. The development/test aggregate confirms order-level totals are not joined into item rows for revenue: item quantities use a separate per-order aggregation, while order value stays on `orders`.

The endpoint uses five tenant-filtered, set-based PostgreSQL queries: conditional summary aggregates, grouped current statuses, a zero-filled grouped outcome trend, per-order item sums with deterministic size buckets, and `GROUPING SETS` for fulfillment/source. It loads neither order entities nor order items into Node, and joins order items only in the isolated quantity aggregate. Existing tenant/created and tenant/status/status-changed indexes serve these paths; Phase 5 adds no index. The `/admin/analytics` page adds **سفارش‌ها و کانال‌ها**, sharing the global period selector and local date/granularity rules.

Lifecycle-duration metrics are deferred because transitions overwrite `status_changed_at`; `updated_at` is not used as an estimate. Reasons, rejection analytics, admin-created order attribution, website-vs-QR distinction, marketing attribution, and payment analytics remain unavailable until UCafe stores those facts. Reservation Analytics remains Phase 6.

## Phase 6: reservation analytics

`GET /api/v1/tenant/analytics/reservations` accepts the shared Analytics period query. It uses the existing tenant context, `analytics.read` permission, and effective `analytics` entitlement, and also requires the effective `reservations` entitlement. The owner page adds a Persian RTL **رزروها** tab. Analytics access projection exposes both effective features so the tab can show the existing unavailable-plan state; the API enforces both features independently.

The domain statuses are `PENDING`, `CONFIRMED`, `REJECTED`, `CANCELED`, `COMPLETED`, and `NO_SHOW`. Pending and confirmed are unresolved/active; completed records an attended reservation; canceled and rejected are terminal; `NO_SHOW` is an explicit staff-recorded outcome. A stale pending reservation is never inferred to be a no-show. Terminal reservations do not transition again, but the row has no status history, so `status_changed_at` is only the latest (terminal) outcome time and direct data repair can restate current-state reports.

Time populations are kept separate. **Reservations created** counts records by cafe-local `created_at`. **Reservations scheduled** counts records by `reservation_date` in the selected calendar range, grouped at `start_time`; this is the operational demand cohort. Each branch's stored timezone interprets the scheduled local date/time, and branch timezones are currently provisioned from the cafe timezone. Outcome trends use `status_changed_at` for the current terminal status. Thus a Monday booking for Friday appears on Monday in the created trend and Friday in scheduled demand.

Status counts and the status breakdown use all reservations scheduled in the selected period. The breakdown share is each current status divided by all scheduled reservations. Operational reserved guests, average party size, party-size distribution, and guest-count peaks use `PENDING`, `CONFIRMED`, `COMPLETED`, and explicit `NO_SHOW`; they exclude `CANCELED` and `REJECTED`. Reserved guests are `SUM(party_size)` over that population. Average party size is the same guest sum divided by the same reservation count and is unavailable (`null`) when the denominator is zero. Party-size distribution reports exact configured party sizes instead of arbitrary buckets.

Rates are calculated on the scheduled-period cohort, with previous-period comparisons using the same formulas. Confirmation rate is `(CONFIRMED + COMPLETED + NO_SHOW) / (PENDING + CONFIRMED + REJECTED + COMPLETED + NO_SHOW)`: cancellations are excluded because current state cannot show whether they were confirmed before cancellation. Completion rate is `COMPLETED / (COMPLETED + CANCELED + REJECTED + NO_SHOW)`. Cancellation and rejection rates use that same terminal-outcome denominator. No-show rate is `NO_SHOW / (COMPLETED + NO_SHOW)`, so unresolved future bookings and canceled/rejected requests do not dilute attendance outcomes. A zero denominator returns `null`.

The report returns all seven Persian-ordered weekdays, all 24 local start-time hours, and a complete 7×24 heatmap. The shared Phase 2 `WeeklyHeatmap` now accepts generic day/hour/numeric-cell accessors and is used by both sales time analytics and reservations; the reservation page switches the selected value between reservation count and reserved guests. Scheduled count/guest trends and date, hour, and weekday peaks are scoped to the selected period. Count peaks include all scheduled statuses; guest peaks use the operational population above. Booking lead time is the average nonnegative interval from `created_at` to scheduled instant for reservations scheduled in the period. Cancellation lead time is the average scheduled-instant minus `status_changed_at` for canceled reservations canceled at or before their scheduled instant.

The implementation uses five tenant-filtered grouped PostgreSQL queries for period summaries, creation trend, scheduled date/hour cells, terminal outcome trend, and exact party sizes; results are not aggregated by loading reservation entities in Node. The existing `(coffee_shop_id, reservation_date, status)` index supports scheduled cohorts. Migration `1790337600000-ReservationAnalyticsIndexes` adds `(coffee_shop_id, created_at)` and `(coffee_shop_id, status, status_changed_at)` indexes for creation and terminal-event scans. No DTO or plan feature was added; the shared Analytics query DTO and the existing Analytics/Reservation effective entitlements are reused.

UCafe stores neither a reservation-to-order link nor a reliable creation-source field; `status_changed_by_user_id` records the latest status actor, not who created the booking. Structured rejection/cancellation reasons and transition history are also absent. Reservation settings are current and unversioned, and reservations have no table assignment, so historical capacity utilization cannot be reconstructed. The page does not infer attendance, revenue, customer identity, marketing source, or capacity from those missing facts.

## Inventory Phase 7 integration

The Analytics page also hosts the Inventory Phase 7 count-to-count usage report at `/admin/analytics`. This report is separate from delivered-sales Analytics definitions and requires both `analytics` and `inventory` permissions and effective plan features. The API reuses Inventory's completed physical counts, immutable movement ledger, valid source references and order-item recipe-version snapshots. Actual depletion is bounded by per-item count timestamps; theoretical usage is signed sale consumption net of valid reversals; known waste and other explained consumption remain separate. Since Phase 8 may store multiple count allocations per item, the report sums those batch/unallocated rows back to one item/location count before calculating actual use. See [INVENTORY.md](INVENTORY.md) for formulas, effective movement timestamps, source validation, the created-at-based order coverage proxy, limitations, endpoints and tests.

The order coverage percentage compares order items created between the count records' completion times with lines having a `SALE_CONSUMPTION` movement; it is not an acceptance-event measure because orders do not retain lifecycle history. Missing recipe usage is never inferred. External sales not recorded in UCafe do not appear in theoretical usage. Historical variance cost is returned unavailable because current balance average cost is not a historical count-time snapshot; no current price is used as past cost. The CTE report executes as one set-based calculation with a tenant/location/item/created-time movement index and returns bounded, separately pageable item rows plus a whole-filter summary.

## Limits and extension

Delivered value is not verified payment. There is no historical status event table, so prior outcomes can be restated by direct data repair. Custom ranges are bounded to 366 days. Refund accounting, guest identity, reservation/order linkage, and multi-branch breakdown remain unavailable. Add a payment/refund ledger before paid-revenue or financial settlement reporting. Inventory Phase 6 menu profitability is a separate current-cost estimate; it does not change delivered-sales revenue or provide historical margin. A future Analytics profitability report needs both Analytics access and a defined historical cost basis. Keep future time-series changes on the established local-time bucketing rule and leave Overview definitions intact.
