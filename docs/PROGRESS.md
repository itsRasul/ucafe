## Inventory Phase 3: order consumption and reversal

Implemented `UNDER_REVIEW → PREPARING` consumption and operational cancellation reversal through the canonical `OrderingService.updateStatus` path. Order status, inventory movements/balances, and notification enqueue share the same PostgreSQL transaction. Consumption is inventory-entitlement-aware; missing optional recipes are warned and skipped, while a configured recipe without a valid active version fails atomically. Recipe quantities are normalized exact decimals; variant recipes precede base recipes. Reversal references and restores original consumption movements even if recipes or entitlement later change.

Migration `1787851200000-IntegrateOrderInventory` adds order-line/recipe/reversal references and database uniqueness/validation. Movement rows keep generic source type/ID alongside structured order and recipe references. No old/in-flight accepted orders are backfilled. There is no order edit, partial cancellation, modifier, customer cancellation, refund, or cost snapshot flow; current checkout supports offline payment and no modifiers. Failed transitions can be retried because the order state and stock ledger roll back together.

Receipt posting reuses `InventoryService` inside a transaction. Purchases use integer toman prices; actual unit costs are normalized to base units and the balance weighted average updates only when a receipt posts.
