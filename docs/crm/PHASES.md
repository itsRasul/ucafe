# Platform CRM implementation phases

Phase 0 is complete as architecture and documentation. Phases 1–7 are implemented. Phases 8–10 remain future work.

| Phase | Objective and scope | Depends on | Explicit non-goals | Update |
|---|---|---|---|---|
| 0 — Architecture | Discover current domains, define ownership/model/lifecycles/integrations, record decisions, and prepare agent guidance. | Existing UCafe source and docs. | No CRM runtime code, migration, UI, Sales Engine, or infrastructure. | Completed in this documentation set; root PRD, Architecture, Business Rules, Current State, Progress, and Decisions link to it. |
| 1 — Organizations & Contacts | Add platform-scoped Organization/Contact records, validated CRUD/search/pagination, archive/restore, exact duplicate candidates, platform permissions, and optional Tenant link support. | Phase 0; existing PostgreSQL, migration, platform RBAC, Next.js route patterns. | No Leads, Deal pipeline, sales analytics, tenant write action, or tenant CRM. | Implemented in migration `1790510000000-CreatePlatformCrmOrganizationsAndContacts`; actual schema/API/UI/permission/test behavior is documented in DATA_MODEL, API, UX, PERMISSIONS, and TESTING. |
| 2 — Lead management | Add Lead capture/assignment/status/history, qualification, unqualification, duplicate handling, conversion to Organization + Contact, and safely link public consultation submissions by unique source request. | Phase 1; current PlatformOrders intake and phone privacy. | No Deals/pipeline or outbound campaigns. | Implemented in migration `1790520000000-CreatePlatformCrmLeads`; API, Persian RTL pages, CRM docs, and tests record actual behavior. Conversion deliberately creates no Deal. |
| 3 — Deals & pipeline | Add one default pipeline, Deal outcomes/loss reasons, stage history, estimates, operational stage totals, list/detail, and pipeline board. Allow a Deal to reference a qualified or converted Lead and its Organization/Contact. | Phases 1–2; fixed default stages documented in PIPELINE. | No custom pipelines, subscription mutations, payments, or forecast-as-revenue. | Implemented in migration `1790530000000-CreatePlatformCrmDeals`; API, Persian RTL UI, docs, and unit/controller/PostgreSQL tests cover actual behavior. Deal creation from a qualified/converted Lead is explicit and unique; Phase 2 conversion still creates no Deal. |
| 4 — Activities, Tasks & Notes | Record historical interactions, future follow-up tasks, notes, assignment, due/completed state, and audit rules. | Phase 1; Phase 2/3 links where available. | No VoIP, email sync, WhatsApp/SMS integration, reminders, automation, or unified timeline. | Implemented in migration `1790540000000-CreatePlatformCrmWorkRecords`; API, Persian RTL UI, activities/tasks/domain/API/permission/integration/event/testing docs, and unit/controller/PostgreSQL tests describe the actual behavior. |
| 5 — Timeline & Organization 360 | Assemble CRM histories and work records into a linked read view and composed Organization workspace. | Phases 1–4; durable source records and selected transactional Task audit actions. | No event sourcing, generic audit feed, duplicate source state, or CRM analytics. | Implemented at read time with `/organizations/:organizationId/overview` and `/timeline`; no Timeline table. |
| 6 — Tenant / Trial / Subscription integration | Show live Tenant, Trial, Subscription, and Plan context; link/unlink an existing Tenant explicitly; show only supported durable account/payment facts in Timeline. | Phase 1; existing owner projections, payment ledger, and platform permissions. | No CRM provisioning, lifecycle/payment mutation, duplicated entitlement state, or fabricated status history. | Implemented with `subscriptions.read`, additive migration `1790550000000-CrmCustomerContext`, explicit transactional link/unlink, read-only owner projections, and bounded query-time Timeline rows. API, UX, INTEGRATIONS, EVENTS, PERMISSIONS, TIMELINE, and TESTING document the contract; D-080 records the boundary. |
| 7 — Custom fields, tags, saved views & Segments | Add typed per-record custom fields, normalized CRM Tags, a bounded shared filter AST, owner-scoped saved views, and dynamic query-based Segments for Organizations, Contacts, Leads, and Deals. | Phases 1–6 stable record types, migration path, platform RBAC, and indexed list APIs. | No nested/general-purpose query language, static Segment members, customer-campaign audiences, custom pipelines, scoring, or workflow automation. | Implemented in `1790560000000-PlatformCrmFieldsTagsViewsSegments`. API/UI/docs cover typed validation, stable option IDs, archive retention, parameterized server filtering, PRIVATE/SHARED view ownership, dynamic preview/count/page results, and audit privacy. D-081 records the model. |
| 8 — Lead prioritization | If operators have enough outcome data, add a transparent and explainable prioritization rule. | Stable Lead sources/status history and operator evidence. | No opaque AI score or autonomous sales action. | Update LIFECYCLE, ANALYTICS, UX, TESTING, and explainability/privacy notes. |
| 9 — CRM workflow automation | Add bounded, opt-in CRM reminders/rules only after notification and worker capacity are validated. | Task model, event/delivery contract, operational limits. | No Sales Engine, mass campaigns, generic workflow engine, or uncoordinated API timers. | Update EVENTS, TIMELINE, INTEGRATIONS, OPERATIONS, PERMISSIONS, TESTING, and decisions. |
| 10 — CRM analytics | Add platform-scoped funnels, conversion, time-in-stage, loss, activity, and task measures from retained CRM history. | Phases 1–9 as relevant; definitions and enough data. | No Tenant Analytics coupling or claimed paid revenue without verified payment source. | Update ANALYTICS, DATA_MODEL, API, UX, TESTING, and decisions. |

Phase numbering is a planning guide, not authorization to build future scope in an earlier phase. Re-scope only when discovery identifies a real prerequisite or the product owner changes the roadmap.
